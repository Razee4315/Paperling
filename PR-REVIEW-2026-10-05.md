## PR #263 — hold for file safety

Head: `ed2fce60ea9634bd25845624ec03d4dc409bc178`. The pointer-event tab reordering and explicit desktop Move left/right actions are useful. The interval check also addresses a real side-by-side editing problem. However, the existing focus-triggered reload/save paths are not safe to invoke continuously while the user edits. These underlying races were already possible on focus; this PR makes them recur every 1.5 seconds without a focus event. They need to be addressed as part of enabling periodic polling.

### P1: edits made during the disk read are discarded

Evidence at the PR head: `src/hooks/useExternalChangeWatcher.ts:58–59`, `src/hooks/useFileSession.ts:327–342`; new interval subscription at `src/hooks/useExternalChangeWatcher.ts:71`.

```ts
if (contentRef.current === originalContentRef.current) {
  await reload(path);
}
// loadFileDirect:
const fileData = await readTextFile<FileData>(path);
// ... no check that the buffer is still the one that was clean ...
setContent(fileData.content);
setOriginalContent(fileData.content);
```

Reproduction: open a clean file, modify it externally, let the interval start a disk read, type into the editor while that read is pending, then complete the read. The newly typed text disappears and the buffer is marked saved, without a conflict prompt. The deterministic hook test expected `my edit while read is pending` and received `external edit`.

This also reproduced in the actual browser frontend with the existing fake disk. Autosave was disabled for this reproduction. A wrapper delayed only the reload's `read_file` call; the editor accepted a real keyboard `y` while the read was held. Before release the buffer ended in `External edit.xy` and the tab reported unsaved changes. After release it became `# Disk update during typing\n\nExternal content.`, the tab reported saved, and no conflict dialog appeared. The loading overlay did not stop keyboard input into the focused editor.

Proof: [before reload](review-evidence/pr263-before-reload.png), [after reload](review-evidence/pr263-after-reload.png).

Concrete fix: capture the target tab identity, path and content revision before stat/read; revalidate them after each await. Apply a silent reload only if that same buffer is still clean and unchanged. Otherwise preserve the user's text and raise a conflict. Reload should not reuse a general file-opening operation that unconditionally clears review/conflict state and replaces live content.

### P1: an in-flight autosave can overwrite external changes after the conflict appears

Evidence: `src/hooks/useExternalChangeWatcher.ts:57`, `src/hooks/useFileSession.ts:713–717`, `src/hooks/useAutosave.ts:84–86`; polling exposes the overlap through `src/hooks/useExternalChangeWatcher.ts:71`.

```ts
knownMtimeRef.current = info.modified;
// diskChangedSince, after its own stat resolves:
const known = knownMtimeRef.current;
return known > 0 && info.modified > known ? info.modified : null;
// an already-running autosave continues after beforeWrite:
if (beforeWrite && !(await beforeWrite(filePath))) return;
const mtime = await saveTextFile(filePath, content);
```

Reproduction: the user has dirty text and autosave's pre-write stat is pending. The interval detects an external modification, absorbs its mtime, and opens the conflict prompt. Release the older pending autosave stat with that same external mtime: it now compares against the advanced value and concludes that nothing changed. `save_file` runs with the local text without the user choosing Keep my version.

The regression uses dirty text at 1490 ms, autosave stat pending at 2990 ms, and interval conflict at 3000 ms. It confirms that the prompt exists before releasing the stat and then observes the unapproved save. Clearing an effect's timer cannot cancel its callback once it is awaiting the stat.

An additional browser observation showed the same unsafe mtime advancement during a clean-buffer reload: after the interval began a held read, a keyboard edit autosaved over the external disk text before the held read was released. The three hook cases are the deterministic evidence; this additional browser observation was not added as a fourth automated case.

Concrete fix: retain the last accepted disk version until explicit conflict resolution or a successful validated reload. Track detected external versions separately for toast deduplication. Invalidate pending autosaves when a conflict, reload, document switch or review intervenes; recheck the current operation generation and conflict state after the async guard, immediately before writing. Add regression coverage for both a pending stat and a pending reload. Preserve explicit Keep my version behavior.

### P2: a stale interval result switches the user back to an old tab

Evidence: `src/hooks/useExternalChangeWatcher.ts:49–59`, `src/hooks/useFileSession.ts:359–361`; polling subscription at `src/hooks/useExternalChangeWatcher.ts:71`.

```ts
const path = filePathRef.current;
const info = await invoke("get_file_info", { path });
const known = knownMtimeRef.current ?? 0;
// ... path can still be A while these live refs now describe B ...
await reload(path);
// loadFileDirect reactivates the existing loaded tab:
setActiveTab(existing.id);
```

Reproduction: let A's interval stat wait, switch to B, then return A's newer mtime. The handler reads B's live refs, reloads A and makes A active again. The hook test expected active path `C:/b.md` and received `C:/a.md`. This disrupts navigation and can also clear overlays belonging to the newly selected tab.

Concrete fix: associate each check with a captured tab/path and reject stale results. If the target became a background tab, refresh only that tab after checking its latest state; do not reactivate it. The background path's new check after stat is a useful start, but the same identity/cleanliness checks must also protect completion of its subsequent disk read.

## Existing strengths, feature gaps and order of work

Preserve the raw-HTML then strict sanitization pipeline, atomic native file writes, centralized shortcuts and explicit conflict choices. The PR's visible-window polling and overlap guards are good resource-management choices. Background stat completion now rereads the latest tab, which is directionally correct. The existing fake disk makes state/command flows reproducible without touching user files.

Compared with established Markdown editors, reliable coexistence with external editors and agents is an essential file-safety feature; it has higher impact than tab-drag animation. Mouse reorder plus explicit Move left/right improves tab management, while native macOS interaction still needs an acceptance pass. The previously documented native fullscreen and distribution-channel gaps remain outside these PRs. This review did not repeat an exhaustive competitor audit.

Suggested order: (1) accept the small #247 update after ordinary integration checks; (2) repair #263 reload/save operation lifetimes and turn the three reproductions into permanent regression tests; (3) address docs compiler/override compatibility and align Node types; (4) repair the editor and Windows dependency graphs with platform CI. Fix #263's data-safety blockers before enabling its polling for users.
